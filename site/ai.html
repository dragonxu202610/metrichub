当 AI 遇到指标

AI 编程工具让"写 SQL"的成本归零，反而放大了语义事故：语法正确但口径错误的查询如今秒出、秒执行、秒扩散。 所以语义层的优先级被 AI 提高了，不是降低了。下面是五个真实问题的完整链路——每一步都是可追溯的。

01三层递进

L1 · 上下文注入把指标定义注入 prompt——消灭同义词歧义、隐式默认、时间语义三类失败根因。AI 读的是口径，不是猜。
L2 · 工具化调用AI 不生成 SQL，调用 query_metric()——SQL 由语义层编译，口径错误在架构上不可能发生。对应 Cube MCP 的 leading pattern。
L3 · 口径自动治理（路线图）AI 起草新指标 YAML → 校验 → 人审 → 注册。语义层从被消费升级为被维护。

02五个问题的完整链路

每张卡片：注入的上下文（L1）→ 工具调用（L2）→ 语义层编译的 SQL → 结果 → 以及"裸 text-to-SQL 会错在哪"。

这不是一次现场 LLM 推理：以下五条链路由 build.py 在构建时预计算并落成 JSON 快照 （api/ai_demo.json），用于演示架构与口径流转，页面上不会发生模型调用。 真实接入形态是：同一份 ai_context() 注入 prompt → 模型返回 query_metric 工具调用 → 语义层 query() 执行 → 结果回填。两者共用同一段编译逻辑，差别只在"谁来选指标和维度"。

诚实边界

语义层是必要条件而非充分条件——指标覆盖不全时 AI 仍会退回裸 SQL，复杂探索仍需人；语义层自身也需要治理（谁批准新指标？口径变更谁签字？）。本演示的五问均为预计算的真实链路（build.py 执行），非 LLM 现场生成——演示的是架构，不是模型能力。
