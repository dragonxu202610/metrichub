02 · Semantic Layer

语义层构建

metrics.yaml 是全站唯一事实源：__METRIC_COUNT__ 个指标的口径、粒度、可加性、 负责人、版本、争议与已知缺陷全部显式注册。引擎（semantic.py，约 116 行）提供三个能力： compile() 把定义编译成 SQL、query() 是 AI 工具调用的底层、ai_context() 生成注入 LLM 的上下文。 生产对应物：dbt MetricFlow / Cube。

1构建流程：七步，每步有门禁

指标不是"写完就上线"——每一步的输出都是下一步的门禁输入，谁签字、机器查什么，全部显式。

1
需求
业务问题 / 拆解树缺口 → 一句话口径 + 单位 + 粒度。basis 表不存在或埋点缺字段 → 先补数，不是先写 YAML（北极星树 2 个叶子"无定义"即此结论）。
2
草案
写进 metrics.yaml。门禁：8 个必填字段、命名正则、group/window/unit 枚举、grain 必须显式声明。
check.py · 口径契约
3
评审签约
定 owner、version=1、notes 记录争议与边界。"承诺 × 实现"检查：desc 里的承诺词（如"排除测试账号"）必须有实现或 notes 承认，否则告警"这句会被追问"。
check.py · 承诺×实现
4
注册
北极星类受唯一性断言：approved 恰好 1 个，且全站文案不得把候选表述为"推荐北极星"——按 title 匹配而非 name（按 name 拼匹配串会恒真通过，比没有断言更危险）。
check.py · 北极星唯一性
5
门禁验证
数据侧：序列非空、序列末点 ≈ 窗口聚合（容差 max(5%, 2pt)——拦"比率被逐日求和"）、ttfc 只剩 0/1440 即 FAIL（口径退化）、队列末点腰斩告警。
check.py --data · 八道门禁之一
6
发布
build → 静态站 + api/*.json。catalog 条数 = 源条数（产物过期 FAIL）；每指标 grain/series_grain 与定义一致；产物严格 JSON（parse_constant 拒绝 Infinity/NaN）。
check.py · 前端×产物契约
7
变更管理
口径修改 → version+1 且 notes 记录旧口径事故。compare_out 拦"改了源没 rebuild"；evidence 逐数字复算；verify_served 抓线上渲染。分歧未决 → 双口径并存（见第 3 节）。
三道产物侧门禁

3口径争议治理：分歧可见，而非互斥

不裁决唯一"正确口径"——每个口径独立注册（独立 name + version + notes 互链），看板并排展示、AI 上下文同时注入，消费端按问题选口径。

激活定义已实现
  • activation_1d（v2，注册当日首次成功）——增长派
  • activation_7d（观察期 7 天）——产品派
  • 合并必然有人被代表；各带 cohort_maturity_days 标注末点截断
渠道归因已实现
  • first_touch $2,829——看获客质量
  • linear $1,693——看助攻价值
  • notes 显式记录：线性口径在演示数据上「不可用于预算决策」（40% 收入无归属）

这与指标工程的经典反例同构：「客单价（按单）vs 人均消费（按人）——两个口径都对，但必须有两个名字，不能共用一个」。 双口径双名字、notes 互链，是同一条纪律。

反例：什么时候不并存 model_gross_margin v2 强制现金口径（33.1% → 12.9%），因旧口径已被证伪（白送额度的燃烧记成收入）—— 这不是分歧而是错误，升版替换、notes 留痕即可追溯。分歧并存，错误升版——两者的区别是治理判断，不是技术判断。

5与 dbt 数仓层的分工边界

dbt：表怎么来已实现
  • 分层建模（staging/DWD/DWS）、行级测试、ref() 血缘
  • 2 项守恒断言（现金精确、分摊 ±$0.05 回现金）
  • 治理痕迹：schema.yml 注释 + 测试挂载在血缘图上
语义层：指标怎么算已实现
  • 口径 / 粒度 / 可加性 / 版本 / 争议记录
  • 治理痕迹：notes + 北极星唯一性 + 承诺×实现检查
  • 互引：basis 只能指 dbt 模型；改口径需确认 dbt 测试仍守恒
口径归属分层（隐性决策显式化） 本项目的口径横跨两层：分摊口径在 dbt 层（dws_model_day 的"现金按积分占比分摊到模型"——需要跨表 join，单表引擎做不了）、 比率口径在语义层（expr 内的 ÷ 与 nullif）。这是自研引擎无实体图下的必然切分，不是疏忽； 生产演进方向是 MetricFlow 的 ratio/derived 指标把分摊口径上收语义层，dws 退化为缓存—— 「物化是缓存，语义层仍是口径源」（语义层工程指南 §8 混合策略）。切分本身写进文档，是因为 两层口径的变更流程不同：dbt 层改分摊要走守恒断言，语义层改比率要走 golden 回归。

6能力边界诚实表

按编译理论的四条规则（语义层工程指南 §3）组织本引擎的能与不能： R1 路径解析——非法维度抛错✓（白名单即路径）；R2 跨事实维度可达——不支持（无实体图，跨表靠 dbt 宽表）； R3 扇形膨胀——单表聚合天然免疫（代价正是 R2）；R4 时间对齐——date_field 即时间锚点声明✓， 但无时间骨架（time spine），粒度转换/同期对比/空日补齐做不了。

不支持当前绕法生产对应物
派生 / 比率指标（指标间运算）双聚合手写进单条 expr（creations_per_active_user）MetricFlow derived/ratio metric
跨模型 joindbt 预 join 成宽表（dwd_task_ch 才让北极星可按渠道归因）MetricFlow entity join / Cube joins
时间 spine / 任意窗口窗口固定 {1d,7d,14d,30d}，超出报错time spine 模型 + 任意粒度
行/列级权限无（单租户演示，见应用层的治理落位）Cube data access policies
方言无关 SQLexpr 是 DuckDB 片段，换引擎即失效编译到各方言
实时出口 / MCPAI 问答为构建时 JSON 快照（AI 页已标注）Cube REST/GraphQL + MCP

时间骨架的修法是 dim_date 日历表（连续无缺口），落地后解锁日→周→月粒度转换、YTD/同期对比与空日补齐—— 当前演示窗口固定 14 天且数据自带全日历，故列为演进项。生态侧注记：Open Semantic Interchange（2025-09，Snowflake/Salesforce/dbt 发起） 与 MCP 正在把语义层从各家私有资产变为可流通资产——本项目的 YAML 结构即按"可被 OSI 描述"的形态组织。
