业务解构

本站全部业务设定（数据模型、指标、模拟行为）都建立在这一页的推断之上。 推断不准，后面只会更不准——所以先把推断亮出来，而不是藏在代码里。

推断声明：以下画像基于公开信息（此类平台的产品面、融资报道、招聘信息）推断，不涉及任何公司内部数据——每条设定的具体出处见 公开信源 页。 所有标注 推断 的内容均欢迎被事实修正——修正画像后重跑 build，指标体系随之更新，这正是"口径即代码"的工作方式。

02团队构成与各域目标 推断

百人级平台的公司画像：工程师约占四成，增长侧（SEO 内容/红人/投放）可能是最大的非技术团队——SEO 往往是此类产品的创始人本行。

团队规模推测关心的目标（= 对数据的真实需求）
CEO / 创始人—ARR 增速、盈利、模型毛利、SEO 天花板 → 一张可信的"公司记分牌"
SEO / 内容15-20关键词排名、落地页×语言矩阵的转化 → 页面 ROI 口径
红人 / 投放8-12CAC、ROAS、归因（首触 vs 线性的裁判只能是数据团队）

模型接入 / 评测5-8各模型成功率/时延/单秒成本 → 模型毛利与流量分配
商业化3-5付费转化、ARPPU、churn、积分池健康度
数据团队3-4服务以上全部 → 本站要回答的问题：一个人如何不被取数淹没

03公司北极星 推断

北极星 = 周活跃创作者数（有多少人在持续得到价值）。理由是计数器可以被少数重度用户 或赠送额度撑起来，而订阅制的续费信号是"人"——按人计量天然抗灌水，且增长、产品、模型三个域都能影响它。 次数与分钟数降为消耗口径。当前生效的北极星以 metrics.yaml 的 north_star_status: approved 为唯一事实源。 → 看完整论证与推翻条件

05阶段诊断：为什么此刻是语义层

STAGE 1 · <50 人野蛮生长期

无专职数据，工程师手写 SQL 查生产库。烟囱式是理性选择：快、贴身、零前置投入。

STAGE 2 · 50-200 人口径爆炸期（本画像所处）

多团队都要数：三个团队三个"付费用户"，会上数字打架；数据岗刚设立，需求开始排队。

STAGE 3 · 200+ 人平台化期

自助分析、语义层产品化、数据 BP。现在就建平台 = 过度设计。

烟囱式的优点（不该被简单否定）

  • 需求到报表零协调成本，贴身服务
  • 口径就是业务方自己定的，永远"对"
  • 零前期投入，分析用完即弃、试错友好

烟囱式在口径爆炸期的代价

  • 口径分裂 → 信任崩塌从"数字打架"开始
  • 同一张底层表被五个人各写一遍 SQL
  • 人离职报表成黑盒，错了没人知道

统一数仓的价值

  • 指标字典 = 全公司度量衡，口径唯一
  • 加工一次全公司消费，边际成本递减
  • 分层边界即质量检查点，血缘可追溯

统一数仓的失效场景（高阶谈资）

  • 中间层建设期业务等不起 → 被骂"慢"
  • 需求排队 → 业务绕过平台导 Excel，shadow IT 复活
  • 过度分层：一次性分析也走五层加工

处方：轻量统一 （由此推导出本站的形态）

该统一的统一：指标口径、核心链路（收入/成本/漏斗）、埋点规范；该放权的放权：探索性分析、一次性报表。 3-4 人数据团队的第一步不是搭平台，而是把口径变成机器可执行的单一事实源——于是有了 metrics.yaml，有了这个站。
